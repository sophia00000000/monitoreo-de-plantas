EVALUADOR DE PLANTAS - EXPLICACION DEL DISENO

1. OBJETIVO
La aplicacion recibe especie, humedad, iluminacion y temperatura. Busca los rangos propios de la especie y clasifica cada criterio como BAJO, OPTIMO o ALTO. El indice de vitalidad resume el estado de la planta.

2. ARQUITECTURA MVC
 Frontend: frontend/index.html, frontend/app.js y frontend/styles.css son archivos estaticos servidos por separado. La comunicacion se realiza con fetch y JSON, sin formularios HTML tradicionales.

3. POR QUE LA SOLUCION CUMPLE SOLID
La solucion aplica SOLID porque separa las responsabilidades, depende de contratos y permite extender el comportamiento sin modificar el codigo que ya funciona.

S - Single Responsibility / Responsabilidad unica
Cada clase tiene una razon concreta para cambiar. Por ejemplo, cambiar JSON por CSV afecta al adaptador, no al evaluador.

O - Open/Closed / Abierto y cerrado
El sistema esta abierto para extension y cerrado para modificacion:
No es necesario modificar el controlador ni el algoritmo principal de evaluacion.

L - Liskov Substitution / Sustitucion de Liskov
Las clases CriterioHumedad, CriterioLuz y CriterioTemp son sustituibles por cualquier otra clase que implemente Criterio. Todas ofrecen el mismo metodo evaluar(valor) y devuelven el mismo contrato: BAJO, OPTIMO o ALTO.
De la misma forma, AdapterJson puede sustituirse por otro adaptador compatible, como AdapterCsv, sin cambiar PlantaRepository.

I - Interface Segregation / Segregacion de interfaces
Las interfaces son pequenas y especificas:
Una clase que lea datos no tiene que implementar metodos de evaluacion, y un criterio no tiene que conocer Flask, archivos ni HTTP. Esto evita interfaces grandes con metodos innecesarios.

D - Dependency Inversion / Inversion de dependencias
Las reglas de negocio no crean directamente sus dependencias. app.py las ensambla y las inyecta:
El evaluador trabaja con el repositorio y la fabrica, no con el archivo JSON ni con Flask. Por eso se puede probar con un adaptador falso en memoria y se puede cambiar el origen de datos sin cambiar la logica de negocio.

CONCLUSION SOLID
Si manana se agrega la planta "mediterranea", se modifica solo el JSON. Si se agrega el criterio "ph_suelo", se agrega su configuracion, una implementacion CriterioPhSuelo y su registro en la fabrica. El controlador, la vista y Evaluador permanecen reutilizables.

4. API REST
GET /api/plantas
Respuesta: {"plantas": [{"especie": "sansevieria", "criterios": [{"nombre": "humedad", "unidad": "%"}, {"nombre": "iluminacion", "unidad": "lux"}, {"nombre": "temperatura", "unidad": "C"}]}]}

POST /api/evaluar
Content-Type: application/json
Ejemplo de cuerpo:
{"especie":"sansevieria","humedad":40,"iluminacion":300,"temperatura":22}

Unidades de entrada: `humedad` se expresa en porcentaje (%), `iluminacion` en lux y `temperatura` en grados Celsius (C). Los tres campos deben existir y contener valores numericos.

La respuesta contiene la planta, `especie`, `indice_vitalidad`, cada criterio con valor recibido, unidad, minimo, maximo y estado, y una recomendacion por cada parametro fuera de rango.

Cada criterio se clasifica como `BAJO`, `OPTIMO` o `ALTO`. El indice de vitalidad es `SALUDABLE` cuando todos los parametros son optimos, `EN_RIESGO` cuando uno esta fuera de rango y `CRITICO` cuando dos o mas estan fuera de rango.

6. EXTENSIONES
Para agregar una planta, edita configuracion/plantas.csv y agrega sus filas. No se modifica el evaluador, controlador ni el frontend.

Para agregar un criterio, agrega su nombre y rango en el JSON, crea una clase que implemente Criterio y registra el nombre en CriterioFactory. El evaluador y la vista ya trabajan con colecciones dinamicas.

7. DESCRIPCION COMPLETA DE LA ARQUITECTURA
La aplicacion utiliza una arquitectura por capas con MVC. Cada capa tiene una funcion delimitada y se comunica con la siguiente mediante datos y contratos definidos.

Flujo principal de una evaluacion:
1. El usuario selecciona el tipo de planta e introduce los valores ambientales en la vista.
2. La vista envia una peticion asincrona fetch con metodo POST y cuerpo JSON.
3. El controlador recibe la peticion REST en /api/evaluar.
4. El controlador valida que exista un JSON y convierte los valores a numeros.
5. El servicio Evaluador solicita al repositorio la planta correspondiente.
6. El repositorio obtiene las plantas que fueron cargadas por AdapterJson desde configuracion/plantas.json.
7. Evaluador solicita a CriterioFactory una regla para cada criterio configurado.
8. Cada Criterio compara el valor recibido con minimo y maximo.
9. Evaluador construye ResultadoEvaluacion y calcula el estado general.
10. El controlador serializa el resultado a JSON y lo devuelve a la vista.

11. RESTRICCIONES DE EXTENSIBILIDAD
Agregar una planta no requiere cambiar codigo: se agrega su configuracion al JSON con sus rangos.
Agregar un nuevo formato de datos requiere crear otro adaptador que implemente Adapter. El repositorio y Evaluador no cambian.
Agregar un nuevo criterio requiere crear una clase que implemente Criterio y registrarla en CriterioFactory. Esto mantiene la regla aislada y evita modificar Evaluador.
Si un nuevo criterio necesita una unidad distinta, esa unidad debe incluirse en la configuracion y presentarse en la vista sin trasladar la regla al controlador.

13. JUSTIFICACION DE LAS RESTRICCIONES
Estas restricciones evitan que la logica de negocio quede mezclada con la interfaz, el protocolo HTTP o el formato de almacenamiento. Tambien garantizan que la fuente de configuracion sea unica, que los cambios tengan un impacto pequeno y que la aplicacion pueda evolucionar hacia CSV, base de datos, nuevos criterios o nuevas plantas sin rehacer el caso de uso central.
